### 1. A website that works like an app (PWA), not a Flutter app
- **We chose:** a PWA. It's a website you can "install" on the home screen, and it keeps working without internet.
- **Instead of:** a Flutter Android app (what the proposal said).
- **Why:** Judges can open a link on any phone: no APK file, no Play Store, no installing. It can still record audio and work offline, which is all we need.
- **What it means for us:** Visits are stored inside the browser (IndexedDB), not in a phone database. Uploading happens while the app is open, not silently in the background.
- **Change it when:** a real pilot needs background uploads or deeper phone features.

### 2. Frontend: React + Vite + plain JavaScript + Tailwind
- **Why:** These are the fastest tools to build with, and easy for either of us to read. Tailwind keeps the styling right inside each screen's code.
- **Instead of:** TypeScript (slower to write in a short build) or Next.js (we don't need its extra features).

### 3. Backend code layout: routes → controllers → services, plain functions
- **We chose:** three layers, each with one job:
  - **routes** receive the web request
  - **controllers** do the feature's logic and the database work
  - **services** talk to outside companies (Claude, Sarvam)
- **Why:** You always know where to look. We write plain functions, not classes, so the code is quick to pick up.
- **What it means for us:** The only classes are simple data shapes (Pydantic models) and error types.

### 4. One small server: FastAPI + SQLite
- **We chose:** one Python server that serves both the app and the data, with SQLite (a database that's just one file).
- **Instead of:** Postgres or other big databases, which need setup and add nothing for a demo.
- **What it means for us:** One thing to deploy and one link to share. Data resets when we redeploy, so demo data loads on every start.
- **Change it when:** we need more than one server, or data that survives redeploys.

### 5. Sarvam turns voice notes into text
- **Why:** It's the cheapest option for a demo: new accounts get ₹100 free, about 2 hours of audio. It understands Tamil, Hindi and Marathi, and there's no AI model for us to host.
- **Instead of:** Bhashini (free but slow to get access to), or running AI4Bharat's model ourselves (needs an expensive GPU).
- **Change it when:** we go to a real pilot. Bhashini fits a government project well.

### 6. Claude Opus 5.5 writes the coaching packet
- **Why:** We have $500 of Claude credits. Claude writes well in Indian languages, and it can be forced to answer in an exact format, so the app never gets a half-broken packet. It can also remember (cache) our long reference material between calls, which makes repeat calls cheaper and faster.
- **Settings:**
  - If Claude refuses a request, another model automatically takes over.
  - We never send settings this model rejects.

### 7. The AI's reference material goes straight into the prompt, with no search database
- **We chose:** to give Claude the whole knowledge pack every time: the checklist, 16 practices, the government's grade goals and 21 official quotes.
- **Instead of:** a search database that picks relevant pieces ("RAG").
- **Why:** The pack is small enough to send in full. Claude caches it, so this stays cheap. It's simpler, with nothing extra to run.
- **Change it when:** we add whole state handbooks and the pack becomes too big.

### 8. Voice notes are at most 30 seconds
- **Why:** Sarvam's simple upload accepts clips under 30 seconds. Short notes also force clear, specific observations. Meena can record as many notes as needed.

### 9. No login for the demo
- **Why:** Login isn't what we're judged on, and it would cost a day. The teacher's page is protected by a hard-to-guess link instead.
- **Change it when:** real people use it. Then we need CRP, teacher and block-officer accounts.

### 10. Coaching stays private; the block officer sees only totals
- **Why:** Teachers fear inspection. If the boss could read the coaching, teachers would stop trusting it.
- **What it means for us:**
  - The block view shows only counts like "14 of 22 schools need support: Children reading for themselves".
  - Any group smaller than 5 schools is merged into "other", so nobody can guess which school it was.
  - There are no names, notes or scores.

### 11. Check quality with an AI grader first, experts later
- **Why:** We can't recruit education experts in a week. We'll test 50 made-up visits and have Claude grade each packet:
  - Is it specific, with one priority?
  - Can it be done in 5 minutes?
  - Is it backed by sources?
  - Is it respectful and in the right language?
- **Change it when:** mentors connect us with real practitioners.

### 12. All data is made up
- **Why:** No real child audio and no personal data. Schools, teachers, numbers and notes are invented. Test voice samples come only from adults who agreed.

### 13. Advice is backed by real quotes from official documents
- **What:** Dhruv collected the official documents: NIPUN Bharat guidelines, NCF-FS 2022 and the KVS FLN monitoring booklet. From these we built:
  - **the checklist:** the KVS checklist items you can actually see in one lesson, plus 2 we added ("children read themselves", "pair/group work")
  - **16 five-minute practices**, adapted from the official suggested activities
  - **21 short quotes**, each with its page number
- **How we know the quotes are real:** a script (`backend/scripts/check_grounding.py`) checks that every quote appears word for word on its cited page. As of 25 Oct, all 21 pass.
- **What it means for us:**
  - The app only needs the quotes file (`knowledge/grounding.json`), not the 55 MB of PDFs, which stay in Dhruv's `edu-hackathon-fln` folder.
  - Page numbers are PDF page numbers, which can differ from the printed ones.
  - The Hindi, Marathi and Tamil checklist text still needs a native speaker to check it.
- **Instead of:** Claude's built-in citation feature, which can't be combined with the fixed answer format we need.

### 14. Dhruv's bigger design is kept for later
- **What:** Dhruv's `APP_PLAN.md` describes a production-scale system: a bigger database, a separate background worker, two-way sync and logins.
- **Why not now:** It's too much for this build. We keep the simple version (#4) but reuse its best ideas: the checklist/practice/quote design, its safety rules, and the "at least 5 schools" privacy rule (#10).
- **Change it when:** a real pilot with many users and phones. Then APP_PLAN is the blueprint ([futurescope](improvements/futurescope.md)).

### 15. Claude picks from fixed lists; the server fills in the rest
- **What:** Claude must choose **one checklist item** to improve and **one practice** from our library, by their ids. The server then adds:
  - the **need area** (looked up from the checklist item)
  - the **source pages** (looked up from the quote ids)
- **Why:** If Claude typed these freely, the block view's counts could drift ("reading" vs "Reading skills") and citations could be invented. Lookups can't drift.
- **What it means for us:**
  - If Claude names something that doesn't exist, the server sends it back for one more try. If that fails too, the visit shows "Failed".
  - Never rename a checklist item id; add a new one instead, or old packets break.

### 16. Reviewing works offline; approving needs internet
- **Why:** Meena often reads the packet while still in the school, with no signal, so edits are saved on the phone as they're typed. But approving creates Sunita's link, which has to be stored on the server, so it waits for a connection.
- **What it means for us:**
  - After approval the packet is locked.
  - Meena can edit only the parts Sunita will read, not the evidence or sources.

### 17. Each voice note is transcribed once; typed notes skip Sarvam
- **Why:**
  - If writing the packet fails and Meena presses Retry, the notes already turned into text are kept, so we don't pay Sarvam twice.
  - A visit with **only a typed note** never calls Sarvam. That's our backup plan for the demo if Sarvam is down.

### 18. Deadline is 1 Nov; features freeze on Thu 29
- **Why:** The real deadline is Sun 1 Nov; we earlier planned for 25 Oct by mistake. We keep two spare days:
  - **Fri 30:** quality checks
  - **Sat 31:** submit
  - **Sun 1 Nov:** left free in case something goes wrong

### 19. The teacher's text holds only what the teacher should read
- **What happened:** In the first real packet (25 Oct), Claude put a note for the CRP inside the teacher's text: *"[CRP: add an example here]"* in "What went well". The CRP approved it, and approving locks the packet, so the teacher would have seen it.
- **We chose:**
  - **Teacher's parts** are in the teacher's language: strength, priority, practice, materials, demo, agreed action and check. They contain nothing addressed to the CRP.
  - **CRP's parts** are in English and plain words: the summary and the evidence. They use checklist wording, never code ids like `children_read`.
  - **A safety net:** Approve is blocked, on the phone and on the server, while a `[CRP: …]` note is left anywhere in the teacher's text.
  - **Wording:** neutral (we don't know the CRP's gender, so no "बुलाऊँगा/बुलाऊँगी"), no children's names even as examples, and only the 2–4 sources that really support the advice.
- **Why:** The teacher must get clean, respectful advice, and the CRP must never be tricked into sharing a draft.
- **Status:** built on 26 Oct. The prompt rules still need a check on real Claude output.

### 20. Only a teacher's latest agreed action is followed up, and it works offline
- **We chose:**
  - At the next visit, the app asks about the action from the teacher's **most recent** approved visit only. Older unchecked actions are out of date once there's a newer packet.
  - Meena's answer (done / partly / not done, a note, and how useful the teacher found the advice, 1–5) is saved on the phone in an **outbox** and sent when there's signal.
  - Each visit keeps one answer, so sending it twice is harmless, and Meena can change it.
- **Why:** The next visit is in a school without internet too, so the question must be on the phone before Meena arrives. That's what the **offline pack** is for: the phone downloads every school's open actions every couple of minutes while online.
- **Also:** The answer goes into Claude's next packet for that teacher ("agreed: pair reading → partly done"), so the advice builds on what happened.
- **Usefulness rating:** asked by Meena at the next visit, because the teacher has no app to rate in.

### 21. The app is saved on the phone with a ready-made PWA plugin
- **We chose:** `vite-plugin-pwa`. When the app is built, it adds a service worker that keeps a copy of every app file on the phone, plus a manifest and icons so the app can be installed.
- **Instead of:** writing our own service worker. That's more code to get right, for no benefit.
- **What it means for us:**
  - It only works in the **built** app (`npm run build`, or the deployed site), not in `npm run dev`, so test offline behaviour on the built app.
  - Data requests (`/api/...`) always go to the server; only the app's own files are kept.

### 22. Demo history is built from our practice library, not generated by Claude
- **We chose:** the server creates the demo data itself on first start:
  - 22 schools
  - two past visits for one teacher per school, with packets made from the practice library
  - checked follow-ups for the older visits
- **Why:** It's free, gives the same result every time, and needs no API key. The block view only needs counts, and the next-visit card only needs the agreed action. Those action lines are written in each school's language (to be checked by native speakers). The rest of a demo packet says "Demo data" in English.
- **Change it when:** we want realistic old packets to open in full. Then generate them once with Claude and save them as a file.

### 23. Rehearsal sends the whole conversation each turn and stores nothing
- **Why:** Each turn is one standalone call: the packet plus the conversation so far, as text. That's simple, nothing is saved on the server, and there's no long chat state to manage. A rehearsal is capped at 16 lines.
- **What it means for us:** Rehearsal needs internet. Closing the page ends the rehearsal.
